# citere-metrics — Tasks Layer Integration (spec v1)

Companion to `citere_revenue_at_risk_spec_v2.md`. Replaces the platform's task logic with `tasks/tasks.json` (79 tasks, lanes A/B/C, built by `tasks/build_tasks.py`) as the single source of "what to do." Money rules (§1, §7 of the money spec) are unaffected — this spec only changes how work is displayed and tracked.

**Removed as separate entities:** `campaigns`, `label_tasks_awaiting_signoff`, `citere_tasks.track_cards_by_group`, `dashboard.prioritization.recommendations`, the client-side `id = "<pid|run>#<fix_idx>"` construction, `localStorage["citere_task_state"]`. Each was a re-packaging of the same `points[].fixes` data (confirmed in the Step-0 reconnaissance, §3 "Где дубли").

**Kept as is:** `points[].fixes` (full 2,149-card detail, still readable per point), `groups` (topic×zone, still computed by `step_06_prioritization.py`) — but repurposed as a grouping axis inside the new views, not as the primary task list.

## 1. New per-task field: `expected_pp`

`group.impact.expected_pp` does not exist. `expected_pp` today lives only on `campaigns[]` (`step_07_action_center.py:49`), one of the entities this integration removes — do not depend on it.

**Rule — recompute at the task level, in `build_tasks.py`, from the same raw ingredients `step_06`/`step_07` use:**

```
ceiling_pp(task) = gap(task) × lever(task) × 100
expected_pp(task) = [ceiling_pp(task) × k_lo, ceiling_pp(task) × k_hi]
```

- `gap(task)` = demand-weighted average of `groups[].gap` over the groups the task's points belong to (weight = each point's `pt_demand_eff`).
- `lever(task)` = same demand-weighted average of `groups[].lever`.
- `k_lo, k_hi` = closure coefficients from `config/thresholds.yaml`, chosen by the task's `type` (not owner-string): T2/T3/T4 → `owned [0.05, 0.10]`; T5 → `comp_owned [0.10, 0.22]`; T6, Hostile-PR-track → `earned [0.10, 0.22]`; T1 → `ugc [0.05, 0.15]`; T9 → `owned`. Report the mapping used for every type before committing.
- Lane B (T7, T8, T9) and T12 in lane C: `expected_pp = null` by design — lane B is ranked by severity, lane C by `usd_yr`; neither uses a content-closure lever.
- Add `expected_pp: [lo, hi]` next to `usd_yr` in `tasks.json` and as "Expected impact: +X.X–Y.Ypp" in the `tasks.md` per-task block. No `expected_pp_partial` flag needed — this computes for every lane A task from data already on every point.

## 3. Operational fields, derived in the builder

Add to each task in `tasks.json`, computed the same way `owner`/`weeks` already are (majority vote over the task's `fixes`):

```json
"execution": "AGENT | AGENT+APPROVE | HUMAN TASK",
"agent_id": "A1 | A2 | ... | null",
"agent_desc": "<verbatim fixes[].agent string of the majority>",
"mlr_gate": true|false
```

- `execution`: majority over the task's points' `fixes[].execution` (values: `AGENT`, `AGENT+APPROVE`, `HUMAN TASK`); tie → most conservative (`HUMAN TASK` > `AGENT+APPROVE` > `AGENT`).
- `agent_id`: parse the majority `fixes[].agent` string, take the code before the first `/` or `·` (e.g. `"A1/A7 · Page-creation..."` → `A1`; `"B8/C12 · ..."` → `B8`). The six agent strings with no code prefix (client-team tasks) → `agent_id: null`.
- `agent_desc`: the full majority `fixes[].agent` string, verbatim — shown in the UI so the human-readable description isn't lost behind a bare code.
- `mlr_gate = true` if any point's fix has `mlr == "medical-review"`. No forced override for lane B — the derived value stands as is. Confirmed count (corrected from an earlier undercount of 54, which was based on a truncated pid list): 133 of 325 lane B cards are `mlr-compatible` (T7: 0/88, T8: 102/206 — mostly procedural "regulatory decision first" cards, T9: 31/31 — all procedural), 192 are `medical-review`. At the task level: 6 of 9 lane B tasks have `mlr_gate=true`; the 3 `false` are the T9 provider-error-report tasks, entirely procedural.

## 4. Priorities screen## 4. Priorities screen (`#/priorities`) — rebuilt

Replaces `groups`-as-primary-list with `tasks.json`, **grouped by `zone`** (the task's zone field, already present from the split logic), sorted by `Σ usd_per_week` of the zone's tasks descending. Inside each zone, tasks sorted by `usd_per_week` desc.

```
Priorities
├── Zone: STARTING & SWITCHING          Σ $X–YM/yr · N tasks
│    ├── Task 1 (title, owner, weeks, $/yr, $/wk, expected_pp, demand, points, top competitor)
│    ├── Task 2 ...
├── Zone: WEIGHT LOSS                   Σ $X–YM/yr · N tasks
│    └── ...
└── Lane B — Label & regulatory (own section, ranked by severity, no $/week sort)
└── Lane C — Decisions (own section, ranked by $/yr, header "at risk, not recoverable by content alone")
```

- Zone header shows `Σ usd_per_week` × implied annualization, plus task count. This is a new aggregate — not previously shown anywhere; verify it sums correctly against `money_totals`.
- Clicking a zone expands/collapses (client-side), clicking a task opens a detail panel (§6) — no longer a separate `#/priorities?group=` screen; fold that route into `#/priorities?zone=`.
- The three old tables (recommendations / healthy / label) are removed; lane B replaces the "label" table, lane A replaces "recommendations", there is no more "healthy" table (it was groups with no issues — if this needs to stay for completeness, keep it as a collapsed "No action needed" section at the bottom, zero-money, not ranked).
- Tile 6 "Diagnosis & Prioritization" on Overview updates its top-3 to top-3 **tasks** (not groups) by `usd_per_week`, still linking to `#/priorities`.

## 5. Action Center (`#/actions`) — rebuilt

Same task list as Priorities, different lens: status and ownership, not money ranking.

```
Action Center
├── Counters: Open N · In progress N · Done N · Dismissed N   (from task_state.json)
├── Filter: lane (A/B/C) · execution · mlr_gate · status
└── Table: task title · owner · execution · mlr_gate · status · $ at stake/mo · [status control]
```

- **No live status control in the UI.** The platform is fully static (confirmed: no fetch/XHR, no server, `ui_spec.md` mandates "the UI never computes," data is inlined at build time into one `ui/index.html`). Status changes are made by editing `tasks/task_state.json` directly (by hand or via a Claude Code command) followed by a rebuild. Action Center is read-only: it displays whatever `task_state.json` said at build time. Remove the existing `taskAct()` prompt()/localStorage status buttons entirely — they created state that never left one browser and is being retired along with `localStorage["citere_task_state"]`.
- `$ at stake/mo` tooltip keeps the existing non-additive note.
- Every task appears here exactly once, by its stable id — no more 842-of-2149 visibility gap; all 79 tasks are visible, lane A/C have money, lane B doesn't.
- Deep link `#/actions?task=<id>` opens that one task's detail directly (fixes point 11 of the Step-0 report — `__nmGoFix` from the map should now use this).

## 7. Point detail — task link (replaces the "Tasks from this question" fixes list)

Current: shows raw `fixes[]` text for `audience="client"` fixes (`tasksForPoint()`, point detail §967 area).

**New:** one line per lane-A/B/C task this point belongs to (a point maps to exactly one primary task per the money-attribution rule, so normally one line; if a point also appears in an `also_addresses` type, do not create a second task link — `also_addresses` is informational only, shown in the task detail, not surfaced here):

```
This question is addressed by: **Publish a new page — patients resisting medication over side-effect fear**  →
```

- Link text = the task's title verbatim (not a generic "view task").
- Click → `#/actions?task=<id>` (task detail, §6).
- A point has no task when it is **portfolio (`pf=1`), OR a web-panel (R4/R5) position that is holding and
  only monitored** (cause `WORKING`, no label/regulatory card). Measured on cycle 1: 172 of 1,424 points —
  80 portfolio and 92 web-panel R4 `WORKING` points whose only fix card is "Keep this position: monitor…".
  Every api `pf=0` point does have a task (0 exceptions). For these, show "Monitored only — no active task"
  instead, linking nowhere.
- A point may carry **more than one** line: lane B overlaps lane A/C, and a point with T7+T8+T9 cards belongs
  to three lane B tasks. Measured: 1,148 points with one task, 73 with two, 31 with three.
- The raw `fixes[]` text is no longer shown here. It remains fully available in `tasks.json`/`tasks.md` per task and in the underlying data for anyone who opens `platform_data.json` directly — nothing is deleted, just no longer duplicated in this screen.

1. Σ `usd_per_week × weeks` summed correctly reconciles to `usd_yr` per task (sanity, not new — already true in `tasks.json`).

5. No screen still reads `campaigns`, `label_tasks_awaiting_signoff`, `citere_tasks.track_cards_by_group`, or `dashboard.prioritization.recommendations` after this integration — confirm by grep.
